# Hosted SVG generation

Status: proposed; implementation pending.

## Contract

The hosted editor edits a decoded treestamp against a repository snapshot. SVG is an export representation. Opening, editing, note transfer, reset, and change detection must succeed independently of SVG renderer availability. Source format supplies initial export preferences, not a separate editing workflow.

The current implementation violates this boundary: loaded-SVG change detection renders the artifact, and the shared rendering limit can reject that edit. Any two overlapping renders on one server process can produce a busy response; this does not require unusually rapid input from one user. Production frequency has not been measured.

## Editing state

Hosted change detection compares decoded document state, including exact paths, notes, hidden entries, folds, and document settings. Reconciliation changes remain visible as changes against the decoded source. The existing post-transfer baseline for Discard remains distinct from that source comparison. SVG appearance belongs to export preferences and export-result validity; it does not determine whether a tree edit can be accepted.

Source SVG drawing bytes are irrelevant to hosted change detection. Loading uses the embedded document; generating an export produces a new drawing. The hosted application has no source-file write action. Local file-write conflict checks remain the responsibility of the local publication layer.

## Proposed export interaction

The proposed UI uses a **Generate SVG** action alongside the export options. This extra click makes generation deliberate; automatic preparation on entering Export is also viable with the same isolation and waiting behavior. The trigger is a product choice to settle before implementation. In the explicit-action version, entering the tab, editing the tree, or changing appearance does not start rendering. Generate captures the latest accepted treestamp and appearance after pending edits settle.

| State | Experience |
| --- | --- |
| Ready to generate | Generate SVG is available. A matching existing result can be reused. |
| Preparing | Progress appears within Export; duplicate generation is disabled. Returning to Tree remains available. |
| Temporarily busy | For `503 svg_busy` or `429`, preparation stays pending with a waiting message. The browser honors `Retry-After` and retries with jitter. A proposed 30-second overall deadline covers active requests and retry waits. |
| Complete | The actual SVG preview, Copy, and Download use the same generated bytes. |
| Unable to complete | Export explains the error and offers Retry. Accepted edits remain intact. Invalid input and output-size limits are reported directly, without automatic retries. |

Leaving SVG export, changing its inputs, or opening another document cancels the pending browser operation and retry schedule. Late results cannot replace a newer result. A result becomes unavailable for Copy/Download when its document or appearance differs from the accepted export inputs; a previous preview must be cleared or explicitly marked outdated. App theme and preview zoom do not change those inputs.

Transient capacity contention is handled inside preparation, rather than requiring users to discover that reopening a tab retries it. Sustained overload or a service outage can still prevent an export; a button cannot guarantee server capacity. Such a failure must remain confined to export.

## Execution and verification

SVG generation remains outside the HTTP event loop with bounded admission, render-time accounting, and no unbounded server queue. A background thread still shares CPU and memory with the service; responsiveness needs measurement, not just removal of the edit dependency. Only export uses that capacity. A canceled browser request retains server accounting until its admitted work actually finishes. Renderer limits and output errors cannot be applied as a prerequisite for accepting tree edits.

Acceptance tests must establish that:

- Markdown and SVG sources with equivalent decoded treestamps have equivalent editing and change-detection behavior, including reconciliation and Discard.
- Editing works while rendering is occupied, its budget is exhausted, or rendering fails; editing paths never invoke the SVG renderer.
- Generation occurs only on the explicit action or retries belonging to that action; normal contention recovers visibly without losing edits.
- Cancellation, deadline expiry, input changes, and late responses preserve the accepted state and prevent stale downloads.
- Health and editing requests remain responsive under expensive export work; global workload limits still hold across client identities.

Caching policy is a separate design topic. These boundaries and overload behavior must hold with a cold cache. After implementation, current behavior belongs briefly in UI flow and Design; this proposal remains planning context. Accepted ADRs are unchanged.
