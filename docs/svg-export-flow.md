# SVG export experience

Status: next-release implementation; validation and release gates are recorded in the ADR. [ADR 0004](adr/0004-structured-svg-artifacts.md) owns the artifact, codec, safety, and publication contracts. This document owns the web/TUI experience and the release sequence. The existing [UI flow](ui-flow.md) describes shipped/current behavior.

## Decisions

The editor continues to edit one document model. Users choose an export representation independently of the loaded file. SVG is a standalone, editable treestamp artifact. Users save it into their repository and add the README image reference themselves; the application does not create, discover, or maintain that relationship in this pass.

Offer both file export and clipboard export. File export is the main SVG action because the useful result is a file that can be referenced and reopened. Clipboard export copies the complete SVG source, including its metadata, for users who prefer to create the file in another editor. It does not copy raster pixels or a Markdown image tag.

Retire the unfenced Markdown-list style in the next release. Retain fenced Unicode and ASCII branch notations, with the same supported identities in both. Fix exact-path disambiguation before removing list support. Legacy list documents are explicitly unsupported after removal: return a clear unsupported-style error without modifying the file or accepted state. Do not silently interpret them as empty/unmarked documents. There is no permanent legacy decoder or migration feature in this pass; call out the removal in release notes. Unsupported cached list sessions may require reopening the source; cache recovery is not a persistence contract.

## Web editor

Keep the three top-level views: **Tree**, **Export**, and **Info**. Export replaces the current Markdown tab; Tree retains editing controls and its existing text-copy shortcut, labeled **Copy Markdown**. Settings, hiding, and other editing controls remain confined to Tree. Reuse the [shared action and tab conventions](ui-patterns.md); do not add an SVG-specific button style.

Export has a labeled **Output** selector with **Markdown** and **SVG**. It starts with the loaded container's format, or Markdown for a newly created tree/example. Switching it only changes the export view. Preserve the choice during this interaction, without introducing durable preferences or saved sessions.

| Output | Preview | Controls |
| --- | --- | --- |
| Markdown | Exact source that Copy Markdown produces, including managed-region markers/configuration and code fences. The display is deliberately plaintext. | **Branches:** Unicode / ASCII; **Copy Markdown** using the existing secondary copy treatment. |
| SVG | The actual generated SVG image with its exported appearance, not the interactive editor tree and not XML source. | **Appearance:** Light / Dark; **Download SVG** as the primary action; **Copy SVG** as secondary. |

For the first SVG style, omit a redundant style selector. Add one only when a second supported style exists. Loaded artifacts retain their supported appearance; new SVG exports initially use the application's current light/dark theme, then maintain an explicit artifact choice independent of later app-theme changes. The continuous renderer uses a transparent background with black ink for light appearance and white ink for dark appearance. Guides and inline `#` annotations use reduced opacity. The preview supplies a contrasting backdrop outside the image so either appearance remains readable regardless of the app theme.

The preview uses an image resource generated from validated data. Never insert uploaded SVG DOM. Show the complete image fitted to available width, with an **Actual size / Fit width** control and a scrollable preview area for large trees. Keep export actions reachable on short/mobile viewports and give the image an accessible description. Rendering changes follow accepted edits; pending/failed generation must not leave an enabled action silently exporting stale output. Copy and Download use the same generated bytes shown in the preview.

The suggested download name is the loaded SVG basename, or `treestamp.svg` for other sources. Browser download behavior determines the local save location; the app does not claim to overwrite the repository file. A short instruction beneath SVG actions says to save the file in the repository and reference it from the README. Do not generate an image link before a repository-relative destination is known.

**Text to SVG:** load the Markdown document → edit in Tree → Export → SVG → Download SVG (or Copy SVG) → manually save/add the file and README image reference.

**SVG update:** select the SVG file in the repository picker → load metadata/reconcile → edit in Tree → Export → SVG → download/copy the updated artifact → manually replace the repository file. The hosted app continues to have no repository-write capability.

**SVG to text:** load/edit SVG → Export → Markdown → Copy Markdown → manually insert the region into the Markdown document. The loaded SVG remains the source.

## Terminal editor

Keep the existing tree editor and textual preview. They show the editable structure and notes regardless of source format. Do not present them as a faithful SVG appearance preview, and do not print a page of XML as the default SVG preview.

Add **Export SVG…** with the unused `e` binding. Open a compact dialog with the SVG appearance identified, a destination field, and **Save SVG**, **Copy SVG**, and **Cancel** actions. Save is the primary action; Copy requires no destination. Use the loaded SVG appearance or a readable light artifact appearance for other sources; do not infer a terminal's background as a reliable theme preference. The first TUI pass preserves this appearance and does not add an appearance editor inside the save/copy dialog. Graphical appearance editing in the terminal can accompany the later preview experiment; web appearance controls are available in this pass. The destination starts as repository-relative `treestamp.svg`; if that is the loaded source, leave the field empty and identify **Write to document** as the action for updating it. A visible note says that graphical preview is unavailable here and the saved SVG can be viewed in a browser. No graphics/rasterization dependency or automatic browser launch is added in this pass.

Save accepts a new `.svg` file under the current repository, with an existing parent directory, using the existing path/symlink/repository-boundary protections. A different existing `.svg` destination requires an explicit replacement confirmation naming the path. Capture its state for the write and refuse intervening changes. Publish atomically and preserve the original on failure. Reject the loaded source as an export destination; use Write to document for same-source SVG updates. Reject a Markdown/non-SVG destination so an export cannot replace a README with image markup. Creation must also refuse a file that appears after the initial check. Saving a copy must not call the controller's existing `write()` operation, which adopts its destination as the loaded document.

Save or Copy closes the dialog only on success. A successful save reports the exact destination; a successful copy reports that SVG source was sent to the clipboard using the existing platform mechanism. Failure keeps the dialog open with its entered destination intact. Cancel closes it without writing or changing accepted state; it never serves as an undo for an already completed export. Native clipboard-command success and sending an OSC 52 request have different evidence: preserve the current terminal status asking the user to paste to confirm when delivery cannot be verified. Known clipboard failures or transport-size limits retain the document and offer Save SVG; never silently truncate or claim to detect an unacknowledged terminal refusal. Export never changes the loaded source or its dirty baseline, including after a successful save. Cancelling or failing an export returns to the same accepted editor state.

The existing `w` **Write to document** action remains tied to the loaded file. For Markdown, it replaces the managed text region. For SVG, it writes the complete regenerated artifact, with its retained supported appearance (or the reported fallback). Show the source path and container in the document context. A successful source write updates its baseline; copying/exporting elsewhere does not. New trees have no source write target, as today.

The existing text-copy and print actions remain textual, labeled accordingly. A general-purpose new-Markdown-document dialog is not reintroduced. The new destination field exists specifically to obtain an SVG artifact. File export is available for new trees, loaded Markdown, and loaded SVG alike.

## State and implementation boundaries

Keep three concepts separate: loaded source path/container and captured baseline; accepted document plus SVG appearance; and ephemeral export-view selection/destination text. Selecting SVG in an export panel does not change source identity. Changing artifact appearance changes a loaded SVG's publishable content, so its dirty comparison includes that appearance; changing only the preview format does not. Graphical appearance for a Markdown source affects SVG exports but must not dirty the Markdown file. Existing textual branch/count/attribution choices retain their document semantics.

Build the shared reader/writer and container-aware controller operations before wiring UI actions. The controller needs distinct source-write and export-copy operations, plus format-aware preview, dirty comparison, check, and update paths. Reuse one generated artifact for preview/copy/save and expose generation failures without altering the accepted document. All actions await queued edits and validate the accepted revision, reusing the current copy action's stale-session protection. Keep generated artifact transport separate from cache/session envelopes and enforce suitable bounded response/download sizes; request-envelope limits must not silently truncate exports.

On SVG load, retain the exact original file bytes as the source snapshot and regenerate a deterministic candidate from its embedded document and supported appearance. Dirty/check compares that candidate against the original bytes. Manual drawing changes, unsupported appearance fallback, renderer-version changes, or noncanonical serialization can therefore make a newly loaded SVG dirty before curation edits. Explain that the preview was regenerated from embedded data and writing will replace the drawing; never automatically write or silently mark the regenerated file as already saved. A repeated check after writing with the same renderer/document/appearance must be clean. This differs from preserving unrelated Markdown prose and is intentional.

## Delivery sequence

1. **Finish the current release independently.** `ui-polish` includes the connected landing illustration and Tree-only Settings fix from `2a84d36`, plus release refinements. The next-release branch shares that UI history and incorporates the focused Settings regression test from `05509ea`; its additional work records the SVG design. Do not make codec changes, list removal, or SVG implementation prerequisites for this release. Continue release verification and publishing separately; this design does not authorize a push.
2. **Repair the text codec on the next-release branch.** Generalize exact-path registration to syntax-colliding names (including arrows and Git-link suffixes), with exhaustive representative round trips for the remaining styles, entry kinds, roots, targets, notes, and counts. Preserve the round-trip rejection guard for unexpected faults. Document old-reader/new-registration compatibility explicitly. This is a codec defect repair, not a permanent conversion exception.
3. **Remove list support in a separate commit.** Remove its UI/TUI choices, rendering/escaping behavior, and accepted settings; explicitly reject legacy list inputs. Update tests and current-format documentation and release notes. Run core and hosted regression checks. Do not ship this removal ahead of the filename repair.
4. **Build paired SVG support.** Freeze the small envelope schema/version and resource bounds; implement the payload reader/writer, shared composition, pure layout/renderer, and container-aware source updates. Add conversion and publication tests before exposing the format.
5. **Connect web and TUI flows.** Implement the experiences above with the shared engine. Validate clipboard/save failure behavior, responsive controls, accessible preview, and native source updates. Complete the normal UI screenshot review and cleanup before committing UI changes.
6. **Release the graphical format only after end-to-end checks.** Verify each supported input to every supported output, exact-path semantics, safe metadata handling, SVG source updates, deterministic check/update behavior, and actual SVG rendering in a GitHub README. Keep the initial visual style small; a second style in tests proves modularity without adding product controls prematurely.

The next release need not wait on terminal graphics, automatic README linking, additional SVG styles, or raster export. None of these steps blocks the current polish release. The sequence defines dependencies rather than a promised delivery date.

## Follow-up: graphical previews in capable terminals

Investigate optional image previews in terminals such as Kitty and Ghostty after the initial export flow works. Verify the actual capabilities of each target: native SVG handling versus rasterizing SVG and using a terminal graphics protocol, capability detection, remote/SSH/tmux behavior, sizing, and cleanup when leaving the preview. Do not assume that supporting terminal images means supporting SVG directly. Evaluate any renderer dependency, installation cost, and security/resource bounds as part of that investigation. Keep the ordinary text editor/export flow usable when graphics are unavailable. This is a follow-up experiment, not an initial-release dependency or a commitment to a particular terminal library.

## Review

Independently reviewed by two agents on 2026-11-23 against the current web controls, controller, document codec, TUI write flow, and clipboard implementation. Findings incorporated: separate export from source-adopting write; bind replacement to captured destination state; fix filenames before list removal; define regenerated-SVG dirty behavior; omit a TUI appearance editor to avoid mixed draft/source semantics; and preserve honest OSC 52 delivery status. Final review found no remaining blocking issue after those clarifications. The implementation now follows these decisions; the filename repair and list removal remain separate checkpoint commits.
